## Majeur
- M1 — Config d'actions non validée côté DB (latent S3). Repro : un utilisateur avec statuses.manage fait `POST /rest/v1/status_actions` avec `type:"webhook"`, `config:{url:"http://169.254.169.254/latest/meta-data"}` (accepté), ou `type:"assign"` avec `userId` d'un autre tenant. Zod et la revérification n'existent que dans les server actions, contournables via REST. Risque : SSRF / affectation cross-org quand S3 exécutera les actions. Correctif : CHECK/trigger SQL (URL https, ids appartenant à l'org) et revalidation + résolution DNS à l'exécution. Idem visible_roles/editable_roles (uuid[] sans FK, acceptent un rôle d'une autre org : mineur en soi).
- M2 — DNS rebinding sur testWebhookAction : `lookup()` valide les IP puis `fetch(url)` résout à nouveau le nom (TOCTOU). Un domaine attaquant à TTL 0 peut répondre une IP publique à la 1re résolution et 127.0.0.1/169.254.169.254 à la 2e ; POST aveugle avec corps fixe, mais l'oracle de statut ("Le serveur a répondu 4xx", "n'a pas répondu") permet un scan de ports interne. Correctif : se connecter à l'IP validée (agent undici avec `lookup` personnalisé, en-tête Host/SNI conservés), même mécanisme à l'exécution en S3.

## Mineur
- m1 — Rate limiting en mémoire par process : inefficace en serverless/multi-instance (chaque instance a son store) et reposant sur x-forwarded-for forgeable (la clé login = ip+email : changer l'en-tête contourne). Brancher un store Redis/Upstash et n'utiliser que l'IP fournie par la plateforme avant la production. testWebhook limité à 30/min/utilisateur (acceptable).
- m2 — isForbiddenHost incomplet : CGNAT 100.64/10, 198.18/15, multicast/réservés ≥ 224, NAT64 64:ff9b::/96 non bloqués en littéral (test it.fails). Les noms résolus passent par le même filtre.
- m3 — org_has_leads et can_transition (SECURITY DEFINER) acceptent l'org d'un tiers : booléen sur l'existence de leads / configuration de transitions, uuid à connaître (tests it.fails). Ajouter `is_org_member(org)` en tête.
- m4 — Changement de template : la garde "pas de leads" est un contrôle séparé (rpc org_has_leads) avant applyTemplate, et org_has_leads renvoie false tant que la table leads n'existe pas (to_regclass). À la création de la table leads (S3), re-tester l'écrasement avec leads (apply_template_payload refait le contrôle dans sa transaction, avec verrou org : bon design, non testable aujourd'hui). Le remplacement est destructif (suppression statuts/champs/sources) : confirmation côté UI seulement.
- m5 — saveTransitionsAction / saveActionsAction font delete puis insert sans transaction : un échec d'insert laisse le statut sans transitions/actions (robustesse, pas sécurité). Concurrence possible entre deux admins (dernier écrit gagne).
